# Phase 1 Inventory: Query Engine Legacy Deprecation

## Summary

This document is the maintained Phase 1 inventory for the live legacy and hybrid surfaces named in the query-engine legacy deprecation plan.
It records what is still authoritative on the current branch, what is only transitional, and what already looks archival or dead.

The evidence in this inventory is based on the current runtime entry points in `sead.query.api`, the authoritative Autofac registrations in `sead.query.api/Dependency.cs`, the live runtime and helper implementations in `sead.query.core`, `sead.query.composer`, and `sead.query.infra`, the current operational guidance in `docs/OPERATIONS.md`, and a repository-wide reference check for the named `deprecated/*.sql` assets.

## Classification Legend

| Classification | Meaning                                                                                                                                             |
|----------------|-----------------------------------------------------------------------------------------------------------------------------------------------------|
| Live           | The current supported runtime or supported operations still depend on this surface directly.                                                        |
| Transitional   | The surface still exists in authoritative code or operations, but mainly as a migration boundary, compatibility seam, or unresolved exception path. |
| Archived       | The surface is historical material kept in the repository, with no current authoritative runtime or operational role found in Phase 1.              |
| Dead           | The surface appears to be scratch or one-off material with no active references or supported role on the current branch.                            |

## `facet_template` Runtime Reachability Proof

- The repository-wide non-archived code search found no live request-path consumer of `Facet.GetTemplate(...)`.
- Current non-archived references to `FacetTemplate` are limited to the entity model in `sead.query.core`, the EF mapping in `sead.query.infra/Repository/FacetContext.cs`, and the import path in `sead.query.infra/Configuration/FacetRouteConfigurationImporter.cs`.
- The only request-path consumers found for `Facet.GetTemplate(...)` are in `sead.query.composer/Archived/BackBurner/`, which is already archival material and not part of the authoritative runtime.
- The Phase 2 disposition is now explicit: treat `facet.facet_template` as importer/schema compatibility and Phase 5 cleanup scope, not as a live request-path blocker for Phase 2 or Phase 3.

## Findings That Change Later Phases

- Phase 2 has now removed `BogusPickService` from the supported facet and result controller load paths and from the facet/result probe commands by introducing `SupportedRequestPickSanitizer`, and it no longer uses `QuerySetupBuilder` internally.
- Phase 2 has now removed `QuerySetupBuilder` from composed result projection setup, legacy result projection setup, category-count setup, bogus-pick normalization, and the shared category-info path by introducing `SupportedRequestQuerySetupFactory`, leaving only retained base-class and compatibility uses to clean up later.
- Phase 3 has now removed the live facet-content and result fallback branches, so unsupported requests fail explicitly instead of silently routing to legacy execution.
- Phase 3 has now removed the authoritative `IQuerySetupBuilder` and `LegacyResultProjectionHandoffBuilder` registrations from the main API and shared test DI roots.
- Plugin removal still cannot be done as a single delete step, but the repository now has an explicit DI boundary: the facet plugins expose separate legacy, composer, and shared registration groups.
- `facet.facet_template` is not yet ready for removal solely because it looks legacy. Phase 2 has proven that no non-archived request-path code consumes it, so later work should treat it as importer/schema compatibility cleanup rather than as a live request-path dependency.
- The named top-level `deprecated/*.sql` files do not appear to be active operational dependencies on the current branch and can be treated as archival material unless a later phase uncovers an external workflow that still depends on them.
